# 第 3 章　解題前的問題分析

## 適用範圍

本章說明如何在寫程式前整理題目規格、候選空間、資料性質與限制，並從直接解法找出可最佳化的重複工作。

## 適用讀者

- 讀完題目後不知道從哪裡開始的讀者。
- 容易看到關鍵字便套用模板的讀者。
- 常因漏看排序、重複值、負數或輸出規則而失敗的讀者。

## 3.1 重述問題

移除故事背景，將題目改寫成一個資料模型與目標：

```text
每天氣溫 → 對每個位置找右側第一個更大值
課程安排 → 判斷 Directed Graph 是否有 Cycle
城市最少轉乘 → 無權 Graph 最短 Edge 數
連續交易區間 → Subarray 問題
```

重述後要能清楚說出：輸入、輸出與合法答案。

## 3.2 建立資料契約

```text
資料型別：整數 Array
元素數量：0 到 100000
元素範圍：-10^9 到 10^9
排序：否
重複值：允許
允許修改輸入：否
```

資料契約影響：

- Array 是否可能為空。
- 是否能用 Frequency Array。
- Sum 是否需要 `long long`。
- 是否能依排序排除候選。
- 排序是否破壞 Index 或順序要求。

## 3.3 辨識輸出要求

以下是不同問題：

- 是否存在答案。
- 答案數量。
- 任意一組答案。
- 所有答案。
- 最小或最大答案。
- 構造一個合法方案。

如果答案不唯一，測試不應要求和參考程式回傳完全相同內容，而應檢查 Postcondition。

## 3.4 建立候選空間

可能的答案來自：

- 單一元素。
- Pair 或 Triple。
- 連續區間。
- Subset。
- Permutation。
- Tree Node 或 Graph Path。
- 一段整數答案範圍。

候選空間決定直接解法。Two Sum 的候選是所有不同 Index Pair；Subarray Sum 的候選是所有 `[left, right)`。

## 3.5 尋找資料性質

### 3.5.1 排序

排序資料可考慮 Binary Search、Two Pointers、相鄰比較與提早停止。

### 3.5.2 連續性

Subarray、Substring 與 Interval 通常和 Sliding Window、Prefix Sum、Difference Array 有關。

### 3.5.3 單調性

若 Condition 隨答案增大只改變一次，可考慮 Binary Search on Answer。

### 3.5.4 重複子問題

若遞迴多次到達同一 State，可考慮 Memoization 或 DP。

### 3.5.5 關係結構

人、城市、課程、格子移動皆可建模成 Graph；階層關係可能是 Tree。

## 3.6 從直接解法找瓶頸

```text
每次重新計算區間和 → Prefix Sum
每次線性尋找補數 → Hash Table
每次重新找最大值 → Heap 或 Monotonic Queue
反覆計算同一 State → DP
完整枚舉所有答案 → 剪枝、分治或結構性最佳化
```

最佳化前要先說清楚重複工作，否則容易只是在套模板。

## 3.7 反例檢查

針對方法的必要條件建立反例：

- Sliding Window Sum：加入負數。
- Binary Search：讓 Predicate 多次變化。
- Greedy：讓局部最佳導致全域較差。
- Hash Table：要求排序輸出。
- Tree DFS：加入 Cycle。

如果方法無法處理反例，需重新確認其適用範圍。

## 3.8 小案例設計

至少準備：

```text
空輸入
最小合法輸入
全部相同
已排序與反向排序
答案不存在
答案位於第一個或最後一個位置
極端整數
```

小案例同時用於釐清規格。例如「遞增」是否允許相等，可用 `[1, 1]` 判斷。

## 3.9 常見問題與判讀

| 現象 | 可能原因 | 檢查方向 |
|---|---|---|
| 解法破壞原 Index | 排序輸入 | 是否保存 `(value,index)` |
| Sliding Window 漏解 | 單調性不存在 | 是否含負數或狀態不可逆 |
| 只找到一組但題目要全部 | 輸出規格看錯 | 任意、計數、列舉差異 |
| 大測資超時 | 未依 Constraint 選解法 | 候選空間與瓶頸 |
| 重複答案 | 去重語意不明 | Value 去重或 Index 去重 |

## 3.11 本章重點

1. 題目首先是一份資料契約與輸出規格。
2. 候選空間決定直接解法。
3. 排序、連續性、單調性與重複狀態是常見可利用性質。
4. 最佳化應對應明確的重複工作。
5. 反例可用來檢查工具的成立條件。
